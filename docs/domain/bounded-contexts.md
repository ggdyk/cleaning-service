## 🎯 Обзор системы

Система разделена на **7 Bounded Contexts** (ограниченных контекстов), каждый из которых отвечает за свою область бизнес-логики.

### Типы контекстов:
- **Core Domain** (ядро бизнеса): Orders
- **Supporting Subdomain**: Catalog, Payment, Content, Notifications
- **Generic Subdomain**: Identity, Admin

---

## 📊 Схема взаимодействия контекстов

```
┌─────────────────────────────────────────────────────────────────┐
│                      Identity Context                           │
│  Управление пользователями, аутентификация, авторизация         │
│  - User, Role, RefreshToken                                     │
└────────────────┬────────────────────────────────────────────────┘
                 │ Предоставляет: UserId, UserRole
                 │ API: /api/auth/*, /api/users/*
                 ↓
┌─────────────────────────────────────────────────────────────────┐
│                      Orders Context ⭐                          │
│  Управление заказами (ЯДРО БИЗНЕСА)                             │
│  - Order, OrderStatus, Address, TimeSlot, OrderExtraService     │
│                                                                 │
│  ← Запрашивает у Catalog: информацию об услугах                 │
│  ← Запрашивает у Identity: информацию о пользователях           │
│  → Инициирует Payment: создание платежа                         │
│  → Публикует события для Notifications                          │
└───────┬─────────────────────┬───────────────────────────────────┘
        │                     │
        ↓                     ↓
┌──────────────────┐   ┌──────────────────────────────────────────┐
│ Catalog Context  │   │         Payment Context                  │
│  Услуги, цены    │   │  Mock-оплата заказов                     │
│  - Service       │   │  - Payment, PaymentStatus                │
│  - ServicePrice  │   │                                          │
│  - ExtraService  │   │  ← Получает от Orders: данные заказа     │
└──────────────────┘   └──────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                    Notifications Context                        │
│  Отправка email-уведомлений                                     │
│  - EmailNotification, NotificationTemplate                      │
│                                                                 │
│  ← Слушает события от Orders: OrderCreated, OrderStatusChanged  │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                      Content Context                            │
│  Текстовый контент, FAQ, блог, отзывы                           │
│  - Page, FAQ, BlogPost, Review, Translation, CallbackRequest    │
│                                                                 │
│  Review связан с Orders через OrderId                           │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                       Admin Context                             │
│  Административные функции, статистика                           │
│  - Statistics (read-models), UserManagement                     │
│                                                                 │
│  ← Читает данные из других контекстов для аналитики             │
└─────────────────────────────────────────────────────────────────┘
```

## 📦 Детальное описание контекстов

## 1. Identity Context

### 🎯 Цель
Управление пользователями, аутентификация и авторизация.

### 📋 Основные сущности
| Сущность | Описание |
|----------|----------|
| **User** | Пользователь системы (клиент, уборщик, менеджер, админ) |
| **Role** | Роль пользователя (Client, Cleaner, Manager, Admin) |
| **RefreshToken** | Токен для обновления JWT |

### ✅ Ответственность контекста
- Регистрация новых пользователей
- Аутентификация (login/logout)
- Выдача и обновление JWT-токенов
- Управление ролями пользователей
- Хранение учетных данных (email, password hash)
- Профиль пользователя (имя, телефон, email)

### ❌ НЕ отвечает за
- Создание заказов (это Orders)
- Хранение адресов уборки (это Orders)
- Управление услугами (это Catalog)
- Оплату (это Payment)

### 🔌 API Endpoints (примеры)
```
POST   /api/auth/register
POST   /api/auth/login
POST   /api/auth/refresh
POST   /api/auth/logout
GET    /api/users/{id}
PUT    /api/users/{id}
GET    /api/users/{id}/profile
```

### 🔗 Взаимодействие с другими контекстами
| Контекст | Направление | Описание |
|----------|-------------|----------|
| Orders | Identity → Orders | Предоставляет информацию о пользователе (имя, телефон) |
| Admin | Identity → Admin | Предоставляет данные пользователей для управления |

### 📝 Примечания
- Использует JWT для аутентификации
- Refresh token хранится в базе данных
- Пароли хешируются (bcrypt/PBKDF2)

## 2. Catalog Context

### 🎯 Цель
Управление каталогом услуг клининга и их ценами.

### 📋 Основные сущности
| Сущность | Описание |
|----------|----------|
| **Service** | Основная услуга (уборка квартиры, после ремонта, генеральная) |
| **ServicePrice** | Цена услуги (может зависеть от площади, времени) |
| **ServiceCategory** | Категория услуги (основные, дополнительные) |
| **ExtraService** | Дополнительные услуги (мытьё окон, чистка мебели, ковров) |

### ✅ Ответственность контекста
- Создание, редактирование, удаление услуг
- Управление ценами услуг
- Описание услуг (название, описание, параметры)
- Категоризация услуг
- Управление дополнительными услугами

### ❌ НЕ отвечает за
- Создание заказов (это Orders)
- Расчёт итоговой стоимости заказа (это Orders, но берёт цены из Catalog)
- Хранение информации о заказанных услугах (это Orders)

### 🔌 API Endpoints (примеры)
```
GET    /api/services
GET    /api/services/{id}
POST   /api/services          [Admin, Manager]
PUT    /api/services/{id}     [Admin, Manager]
DELETE /api/services/{id}     [Admin]
GET    /api/services/{id}/price
GET    /api/extra-services
```

### 🔗 Взаимодействие с другими контекстами
| Контекст | Направление | Описание |
|----------|-------------|----------|
| Orders | Catalog → Orders | Предоставляет информацию об услугах и ценах |
| Admin | Catalog → Admin | Предоставляет данные для аналитики |

### 📝 Примечания
- Цены могут быть динамическими (зависеть от площади, времени суток)
- Catalog — источник истины для цен (Orders запрашивает актуальную цену)
- Услуги поддерживают мультиязычность (RU/EN)

## 3. Orders Context ⭐ (ЯДРО СИСТЕМЫ)

### 🎯 Цель
Управление жизненным циклом заказов клининга — от создания до завершения.

### 📋 Основные сущности
| Сущность | Описание |
|----------|----------|
| **Order** | Заказ на уборку (агрегат) |
| **OrderStatus** | Статус заказа (New, Assigned, InProgress, Completed, Cancelled) |
| **OrderExtraService** | Связь заказа с дополнительными услугами |
| **Address** | Адрес выполнения уборки |
| **TimeSlot** | Временной слот для выполнения заказа |

### ✅ Ответственность контекста
- Создание нового заказа клиентом
- Изменение статуса заказа
- Назначение уборщика на заказ (менеджером или автоматически)
- Расчёт итоговой стоимости заказа (запрашивая цены у Catalog)
- Управление адресом уборки
- Управление временными слотами
- Добавление дополнительных услуг к заказу
- Отмена заказа
- Валидация бизнес-правил (например, нельзя отменить заказ, который уже выполняется)

### ❌ НЕ отвечает за
- Хранение полной информации о пользователе (только UserId)
- Хранение полной информации об услуге (только ServiceId)
- Логику оплаты (делегирует Payment)
- Отправку уведомлений (делегирует Notifications)
- Аутентификацию (делегирует Identity)

### 🔌 API Endpoints (примеры)
```
POST   /api/orders                    [Client]
GET    /api/orders/{id}               [Client, Cleaner, Manager, Admin]
PUT    /api/orders/{id}/status        [Manager, Cleaner]
POST   /api/orders/{id}/assign        [Manager]
DELETE /api/orders/{id}               [Client (только если New)]
GET    /api/orders/my                 [Client, Cleaner]
POST   /api/orders/{id}/extra-services
```

### 🔗 Взаимодействие с другими контекстами
| Контекст | Направление | Описание |
|----------|-------------|----------|
| Identity | Orders → Identity | Запрашивает информацию о клиенте и уборщике (имя, телефон) |
| Catalog | Orders → Catalog | Запрашивает информацию об услугах и ценах при создании заказа |
| Payment | Orders → Payment | Инициирует создание платежа после подтверждения заказа |
| Notifications | Orders → Notifications | Публикует события для отправки уведомлений |
| Content | Orders ← Content | Content использует OrderId для связи отзывов с заказами |

### 📊 Жизненный цикл заказа (OrderStatus)
```
New → Assigned → InProgress → Completed
  ↓                              ↑
  └─────── Cancelled ────────────┘
```

**Переходы:**
- `New` → `Assigned`: Менеджер назначил уборщика
- `Assigned` → `InProgress`: Уборщик начал работу
- `InProgress` → `Completed`: Уборщик завершил работу
- `New/Assigned` → `Cancelled`: Клиент или менеджер отменил заказ

### 🎯 Ключевые бизнес-правила
- Клиент может отменить заказ только в статусе `New`
- Менеджер может отменить заказ в статусах `New`, `Assigned`
- Уборщик не может изменить заказ после статуса `Completed`
- При создании заказа обязательны: serviceId, address, timeSlotId
- Итоговая цена рассчитывается как: Service.Price + Σ(ExtraService.Price)

### 📝 Примечания
- Orders — это Core Domain, самая важная часть системы
- Все изменения статуса логируются (audit trail)
- При изменении статуса публикуются события для Notifications

## 4. Payment Context

### 🎯 Цель
Обработка mock-оплаты заказов (имитация платёжной системы).

### 📋 Основные сущности
| Сущность | Описание |
|----------|----------|
| **Payment** | Платёж за заказ |
| **PaymentStatus** | Статус платежа (Pending, Success, Failed) |

### ✅ Ответственность контекста
- Создание платежа для заказа
- Имитация процесса оплаты (mock)
- Обновление статуса платежа
- Хранение информации о платежах

### ❌ НЕ отвечает за
- Создание заказов (это Orders)
- Реальную интеграцию с платёжными системами (mock)
- Расчёт стоимости заказа (Orders передаёт уже рассчитанную сумму)

### 🔌 API Endpoints (примеры)
```
POST   /api/payments              [Orders Service]
GET    /api/payments/{id}         [Client, Admin]
GET    /api/payments/order/{orderId}
PUT    /api/payments/{id}/status  [Mock payment processor]
```

### 🔗 Взаимодействие с другими контекстами
| Контекст | Направление | Описание |
|----------|-------------|----------|
| Orders | Payment ← Orders | Orders инициирует создание платежа после подтверждения заказа |
| Orders | Payment → Orders | Payment уведомляет Orders об успешной/неуспешной оплате |

### 📊 Жизненный цикл платежа (PaymentStatus)
```
Pending → Success
   ↓
   └──→ Failed
```

### 📝 Примечания
- Это mock-реализация, без реальной интеграции с банками
- В будущем можно заменить на реальную платёжную систему (Stripe, PayPal)
- Один заказ = один платёж

## 5. Content Context

### 🎯 Цель
Управление текстовым контентом, FAQ, блогом, отзывами и запросами обратного звонка.

### 📋 Основные сущности
| Сущность | Описание |
|----------|----------|
| **Page** | Статические страницы ("О нас", "Контакты", "Условия") |
| **FAQ** | Вопросы и ответы |
| **BlogPost** | Статьи блога |
| **Review** | Отзывы клиентов (связаны с заказами через OrderId) |
| **Translation** | Переводы контента (RU/EN) |
| **CallbackRequest** | Запросы обратного звонка от посетителей сайта |

### ✅ Ответственность контекста
- Создание, редактирование, удаление страниц
- Управление FAQ
- Публикация статей блога
- Управление отзывами клиентов
- Хранение переводов для мультиязычности
- Приём и обработка запросов обратного звонка
- Модерация отзывов (менеджерами)

### ❌ НЕ отвечает за
- Создание заказов (это Orders)
- Валидацию, что OrderId существует (Content хранит только ID)
- Управление пользователями (это Identity)

### 🔌 API Endpoints (примеры)
```
GET    /api/pages
GET    /api/pages/{slug}
POST   /api/pages                 [Manager, Admin]
GET    /api/faq
POST   /api/faq                   [Manager, Admin]
GET    /api/blog
POST   /api/blog                  [Manager, Admin]
GET    /api/reviews
POST   /api/reviews               [Client]
POST   /api/reviews/{id}/moderate [Manager]
POST   /api/callback-requests     [Anonymous, Client]
GET    /api/callback-requests     [Manager, Admin]
```

### 🔗 Взаимодействие с другими контекстами
| Контекст | Направление | Описание |
|----------|-------------|----------|
| Orders | Content → Orders | Review содержит OrderId для связи отзыва с заказом |
| Identity | Content → Identity | Review содержит UserId автора отзыва |

### 📝 Примечания
- Отзывы связаны с заказами: клиент может оставить отзыв только после завершения заказа
- CallbackRequest обрабатывают менеджеры
- Все тексты поддерживают мультиязычность (RU/EN)
- Отзывы проходят модерацию перед публикацией

## 6. Notifications Context

### 🎯 Цель
Отправка email-уведомлений пользователям при изменении статуса заказа и других событиях.

### 📋 Основные сущности
| Сущность | Описание |
|----------|----------|
| **EmailNotification** | Email-уведомление |
| **NotificationTemplate** | Шаблоны уведомлений (для разных событий) |
| **NotificationStatus** | Статус уведомления (Pending, Sent, Failed) |

### ✅ Ответственность контекста
- Отправка email-уведомлений
- Управление шаблонами уведомлений
- Логирование отправленных уведомлений
- Повторная отправка при ошибках

### ❌ НЕ отвечает за
- Определение, когда отправлять уведомления (слушает события от Orders)
- Создание заказов (это Orders)
- Хранение email пользователей (запрашивает у Identity)

### 🔌 API Endpoints (примеры)
```
POST   /api/notifications/send       [Internal]
GET    /api/notifications/{id}       [Admin]
GET    /api/notifications/templates  [Manager, Admin]
PUT    /api/notifications/templates/{id}
```

### 🔗 Взаимодействие с другими контекстами
| Контекст | Направление | Описание |
|----------|-------------|----------|
| Orders | Notifications ← Orders | Слушает события: OrderCreated, OrderStatusChanged, OrderCancelled |
| Identity | Notifications → Identity | Запрашивает email пользователя для отправки уведомления |

### 📧 События, на которые реагирует Notifications
| Событие | Кому отправляется | Содержание |
|---------|------------------|------------|
| `OrderCreated` | Client | "Ваш заказ создан, ожидает назначения уборщика" |
| `OrderAssigned` | Client, Cleaner | "Заказ назначен уборщику X" |
| `OrderInProgress` | Client | "Уборщик начал работу" |
| `OrderCompleted` | Client, Cleaner | "Заказ завершён, ждём ваш отзыв" |
| `OrderCancelled` | Client, Cleaner | "Заказ отменён" |

### 📝 Примечания
- Использует SMTP для отправки email (или mock для тестирования)
- Шаблоны поддерживают мультиязычность (RU/EN)
- В будущем можно добавить SMS-уведомления

## 7. Admin Context

### 🎯 Цель
Административные функции: управление пользователями, просмотр статистики, модерация.

### 📋 Основные сущности
| Сущность | Описание |
|----------|----------|
| **Statistics** | Агрегированная статистика (read-models) |
| **UserManagement** | Управление пользователями (блокировка, изменение ролей) |

### ✅ Ответственность контекста
- Блокировка/разблокировка пользователей
- Изменение ролей пользователей
- Просмотр статистики (количество заказов, выручка, активные пользователи)
- Модерация контента (опционально, можно в Content)
- Dashboard для админов

### ❌ НЕ отвечает за
- Создание заказов (это Orders)
- Хранение основной информации о пользователях (это Identity)
- Бизнес-логику заказов (это Orders)

### 🔌 API Endpoints (примеры)
```
GET    /api/admin/statistics
GET    /api/admin/users
PUT    /api/admin/users/{id}/block
PUT    /api/admin/users/{id}/role
GET    /api/admin/orders/report
```

### 🔗 Взаимодействие с другими контекстами
| Контекст | Направление | Описание |
|----------|-------------|----------|
| Identity | Admin → Identity | Управление пользователями (блокировка, изменение ролей) |
| Orders | Admin → Orders | Чтение данных заказов для статистики и отчётов |
| Catalog | Admin → Catalog | Управление услугами и ценами |
| Content | Admin → Content | Модерация CallbackRequest |

### 📝 Примечания
- Admin Context читает данные из других контекстов, но не изменяет бизнес-логику
- Statistics — это read-models (денормализованные данные для быстрого доступа)
- Доступ только для ролей Admin и Manager

## 🔗 Взаимодействие между контекстами

### Общие принципы
1. **Прямые API-вызовы** — контексты общаются через REST API
2. **Нет прямого доступа к БД других контекстов** — каждый контекст имеет свою базу данных (или схему)
3. **События** — Orders публикует события для Notifications (через message broker или in-process events)
4. **Минимальная связанность** — контексты знают друг о друге минимально (только ID)

---

### Примеры взаимодействия

#### 1. Создание заказа

```
[Client] → POST /api/orders
    ↓
[Orders] → GET /api/users/{userId} (Identity)
[Orders] → GET /api/services/{serviceId} (Catalog)
    ↓
[Orders] создаёт заказ в БД
    ↓
[Orders] → POST /api/payments (Payment)
    ↓
[Orders] публикует событие OrderCreated
    ↓
[Notifications] слушает событие → отправляет email клиенту
```

---

#### 2. Изменение статуса заказа

```
[Manager] → PUT /api/orders/{id}/status
    ↓
[Orders] обновляет статус в БД
    ↓
[Orders] публикует событие OrderStatusChanged
    ↓
[Notifications] слушает событие → отправляет email клиенту и уборщику
```

---

#### 3. Оставление отзыва

```
[Client] → POST /api/reviews
    ↓
[Content] → GET /api/orders/{orderId} (Orders) — проверка, что заказ завершён
    ↓
[Content] создаёт отзыв в БД
    ↓
[Content] → PUT /api/reviews/{id}/moderate (Manager)
```

## ⚠️ Правила и ограничения

### ✅ Разрешено
- Контекст может **запрашивать данные** у другого контекста через API
- Контекст может **подписываться на события** другого контекста
- Контекст может **хранить ID** объектов из других контекстов

### ❌ Запрещено
- Контекст **НЕ МОЖЕТ читать напрямую БД** другого контекста
- Контекст **НЕ МОЖЕТ изменять данные** другого контекста напрямую
- Контекст **НЕ МОЖЕТ дублировать бизнес-логику** другого контекста

---

### Хранение связей между контекстами

**Пример:** Orders хранит связь с User

```csharp
// ❌ ПЛОХО: Orders хранит полную информацию о пользователе
public class Order
{
    public int Id { get; set; }
    public User Client { get; set; } // ← НЕ ДЕЛАТЬ ТАК!
}

// ✅ ХОРОШО: Orders хранит только ID
public class Order
{
    public int Id { get; set; }
    public int ClientId { get; set; } // ← ПРАВИЛЬНО
    // Если нужно имя клиента — запросить у Identity по ClientId
}
```

---

### Правила именования

**Единый язык (Ubiquitous Language):**
- В Orders: `Client` (клиент), `Cleaner` (уборщик)
- В Identity: `User` (пользователь)
- В Catalog: `Service` (услуга)

Используйте термины, понятные бизнесу!
